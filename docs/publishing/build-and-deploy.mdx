模板输出的是静态站点。只要 `out/` 构建成功，就可以部署到支持静态文件的平台。

## 发布前检查 {id="checks"}

建议按顺序执行：

<Aside title="Example">

```bash
npm test -- --runInBand
npm run lint
npm run build
```

</Aside>

- `npm test`：验证文档结构、配置和关键约束。
- `npm run lint`：检查 TypeScript / React 代码。
- `npm run build`：导出静态站点并生成搜索索引。

还应人工检查首页、至少一个文档页、图片、站内链接和搜索。如果生产环境部署在子路径
，使用相同的 `NEXT_PUBLIC_BASE_PATH` 做一次本地构建。

## 生产构建 {id="build"}

```bash
npm run build
```

该命令会：

1. 执行 Next.js 构建与静态导出
2. 生成 sitemap
3. 用 Pagefind 为 `out/` 建立搜索索引

部署目录始终是仓库根目录下的 `out/`。

## 部署到 GitHub Pages {id="github-pages"}

模板已包含 `.github/workflows/deploy-pages.yml`。从模板创建自己的仓库后，不需要
复制额外工作流；它会在每次推送到 `main` 后构建站点、上传 `out/`，再发布到 GitHub
Pages。

首次部署按下面的顺序设置：

1. 使用 **Use this template** 创建仓库，或将模板代码推送到新仓库的 `main`
2. 打开仓库的 **Settings → Pages**
3. 在 **Build and deployment** 下将 **Source** 选择为 **GitHub Actions**
4. 再次推送到 `main`，或在 **Actions** 页面手动运行 **Deploy GitHub Pages**
5. 等待 `deploy` job 完成，从工作流页面或 **Settings → Pages** 打开站点

<Aside title="Example">

普通仓库 `docs-template` 的地址是：

```text
https://<用户名>.github.io/<仓库名>/
```

如果仓库名本身是 `<用户名>.github.io`，站点位于根地址：

```text
https://<用户名>.github.io/
```

</Aside>

工作流通过 `actions/configure-pages` 读取当前仓库的真实部署信息，并在构建时注入
：

- `NEXT_PUBLIC_BASE_PATH`：普通仓库自动得到 `/<仓库名>`，根站点得到空路径
- `SITE_URL`：用于生成带有正确公开地址的 sitemap

因此无需手工填写仓库子路径。Next.js 静态资源、PWA manifest 和 Pagefind 搜索结果
、文档图片都会使用同一前缀。

若默认分支不是 `main`，修改工作流中的 `on.push.branches`。若 Actions 页面没有工
作流，检查文件是否已经存在于默认分支的 `.github/workflows/` 中，以及仓库是否允许
GitHub Actions 运行。

## 其他托管平台 {id="platforms"}

模板输出纯静态文件，平台的核心设置都是构建命令 `npm run build` 和发布目录
`out`：

| 平台             | 构建命令        | 发布目录       | 额外说明                              |
| ---------------- | --------------- | -------------- | ------------------------------------- |
| GitHub Pages     | 工作流内置      | `out`          | 自动注入仓库子路径和站点 URL          |
| Vercel           | `npm run build` | `out`          | 仓库已有 `vercel.json` 和 `cleanUrls` |
| Cloudflare Pages | `npm run build` | `out`          | 设置 Node.js 24 和 `SITE_URL`         |
| Netlify          | `npm run build` | `out`          | 设置 Node.js 24 和 `SITE_URL`         |
| 对象存储 / CDN   | 本地或 CI 构建  | 上传整个 `out` | 托管端需支持目录式 clean URL          |

部署在域名根路径时不设置 `NEXT_PUBLIC_BASE_PATH`。只有站点位于
`https://example.com/docs/` 这类子路径时，才设置 `/docs`。

<Aside title="Example">

```bash
NEXT_PUBLIC_BASE_PATH=/docs \
SITE_URL=https://example.com/docs \
npm run build
```

</Aside>

## 环境变量 {id="environment"}

| 变量                    | 是否必需       | 作用                               |
| ----------------------- | -------------- | ---------------------------------- |
| `SITE_URL`              | 公开部署推荐   | sitemap 的完整公开地址，包含子路径 |
| `NEXT_PUBLIC_BASE_PATH` | 仅子路径部署   | Next.js、搜索和静态资源的 URL 前缀 |
| `PORT`                  | 仅本地预览可选 | `preview:search` 使用的端口        |

GitHub Pages 工作流会自动提供前两个变量。Vercel 可回退到平台域名变量；其他公开站
点建议显式设置 `SITE_URL`。未设置时 sitemap 使用 `http://localhost:3000`，只适合
本地构建。

## 上线后验收 {id="acceptance"}

不要只看到首页就认为部署完成。逐项检查：

- 首页标题、卡片和外链正确。
- 从右上角进入每个大章节，左侧链接都可用。
- 直接访问并刷新一个二级文档 URL。
- 图片和下载文件没有 404。
- 搜索能找到标题、小节和正文，点击结果能到正确锚点。
- 打开 `/sitemap.xml`，确认 URL 使用公开域名而不是 localhost。
- 窄屏下导航、表格、代码块和 Example 可以阅读。

遇到构建或线上问题时，按 [常见问题](/publishing/troubleshooting) 排查。
